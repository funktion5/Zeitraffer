# Plan: x264 CRF 28 as the default video quality

Status: done 2026-10-30. Written (config key, `x264_crf_arguments()` in `src/video.py`, tests, README),
checked on the VPS and saved by Julius. Result on Uferstrasse (Yearly, `medium`): 21.2 MiB at CRF 23
against 9.9 MiB at CRF 28 (53 % smaller), the stored encoder setting reads `crf=28.0`, encode time
36.5 s against 44.4 s; Julius judged it fine by eye. The SLSV comparison (the only 1080p camera) was
offered and not done.

## Goal

Make every video the pipeline encodes about 45 % smaller by raising the x264 quality factor
(CRF) from FFmpeg's default 23 to 28, keeping the `medium` preset. One setting in
`config/config.json`, so nightly runs, web-UI jobs and manual runs all produce the same size
without any per-host environment setup.

## Evidence (measured by Julius on the Pi, 2026-10-21, SLSV Yearly)

| Variant | Size | vs default | Encode time | ffmpeg RAM |
|---|---|---|---|---|
| CRF 23, medium (old default, nightly cron) | 184.0 MB | - | 11:23 min | 489 MB |
| **CRF 28, medium** | **97.6 MB** | **-47 %** | 9:58 min | 491 MB |
| CRF 28, ultrafast | 171.9 MB | -7 % | 1:06 min | 152 MB |
| CRF 23, veryslow | 171.1 MB | -7 % | 90 min | 816 MB |

Clip test (about 20 % of the frames): CRF 23 36.5 MB, SSIM 0.977; CRF 26 25.7 MB, SSIM 0.965;
CRF 28 19.8 MB, SSIM 0.954. Denoise saved only 5 to 6 % more, 720p halves the size but is a
product decision, AV1 saved 17 to 20 % and has a playback risk, veryslow is out. These are Pi
numbers; the VPS (2 cores) has not been measured with CRF 28.

Why medium and not ultrafast: ultrafast at CRF 28 is almost as large as the old default (171.9
vs 184 MB), so the CRF saving is lost. The VPS has no kill rule (that was the Hetzner web server),
so `medium` is fine there.

## Decisions (Julius, 2026-10-30)

- **Option B:** the default lives in `config/config.json` as `timelapse.crf`, with an env override
  `TIMELAPSE_X264_CRF`. The cron line does not change.
- Precedence: env var (if set and not blank) over config value.
- The preset stays as it is (`TIMELAPSE_X264_PRESET`, unset = FFmpeg's `medium`).

## Pieces

1. `config/config.json`: add `"crf": 28` under `timelapse`.
2. `src/video.py`:
   - New `X264_CRF_ENV = "TIMELAPSE_X264_CRF"` and `x264_crf_arguments() -> list[str]`, built like
     `x264_preset_arguments()`: read at call time, not at import, blank env counts as unset,
     value must be a whole number from 0 to 51, otherwise `ValueError` naming the variable.
   - Without the env var the value comes from `CONFIG["timelapse"]["crf"]`, validated by the same
     range check, so a typo in the JSON fails loudly instead of encoding with a bad value.
   - The command becomes `-c:v libx264 [-preset P] -crf N -threads T -pix_fmt yuv420p`.
3. Config structure test (`tests/config_test.py`): add `crf` to `EXPECTED_TIMELAPSE_KEYS` and an
   `int` assertion.
4. Docs, German, short: `README.md` (config example, the `timelapse.*` sentence, env table row
   `TIMELAPSE_X264_CRF`) and one line in `docs/vps.md` next to the preset note. Task 30 of the
   ssh-frames plan also rewrites parts of `docs/vps.md` and the `install.sh` cron hint, so only the
   CRF line is added here; no other doc is reworded.

## Tests first (`tests/video_test.py`, next to the preset tests)

- No env var: `x264_crf_arguments()` returns `["-crf", "28"]` (the config value).
- Env var `26`: returns `["-crf", "26"]`; blank or whitespace env counts as unset.
- Env var `abc`, `-1`, `52`, `23.5`: each raises `ValueError`.
- Bad config value (monkeypatched `CONFIG`): raises `ValueError`.
- The full ffmpeg command test at `tests/video_test.py:~323` gains `"-crf", "28"` after `libx264`;
  one more test checks the order `libx264`, `-preset`, `-crf`, `-threads` when both env vars are
  set.
- `tests/config_test.py` passes with the new key.

## Not in scope

- Re-encoding existing videos. Nightly retention rebuilds them: Dailies roll over in 7 days,
  Weekly, Monthly and Yearly are rebuilt every night, so the library is at CRF 28 within a week.
  A video that must change sooner is rebuilt by hand with the usual job command.
- Per-job or per-camera CRF values, denoise, 720p, AV1.
- The blur/pixelation ffmpeg call (`anonymize`) and the highlights flagger; they do not encode the
  timelapse videos. Verify with a grep that `libx264` appears only at `src/video.py:361`.
- The Pi (retired after the VPS switchover; it only picks this up if someone pulls there).

## Verification (Julius, by hand on the VPS)

1. Pull or rsync, then `python -m pytest` and `ruff check .` plus `ruff format --check .` (CI has no
   FFmpeg, so run pytest with `ffmpeg`/`ffprobe` hidden as well).
2. Build one manual Yearly for a single camera, e.g. SLSV (`--jobs yearly --cameras SLSV`), and
   compare the size with the nightly Yearly from 2026-10-29. Expect roughly half; the Pi value was
   -47 %. Record the number.
3. Watch that Yearly in the web UI and judge quality yourself (SSIM 0.954 is a clip figure, not a
   verdict). Sky gradients and fine foliage are where CRF 28 shows first. If it looks too soft, set
   `crf` to 26 (about -30 %) in `config/config.json` and nothing else changes.
4. The next nightly run's `report.txt` shows the new sizes; the cron line stays unchanged.
